1. EXECUTIVE SUMMARY & PLATFORM OBJECTIVE
================================================================================
CodeComplex is a production-grade, real-time multiplayer competitive programming
and software engineering battle arena. Traditional coding platforms (LeetCode, 
HackerRank, Codeforces) are almost exclusively focused on static algorithmic 
problem-solving evaluated asynchronously through batch test cases.

CodeComplex expands competitive programming into modern full-spectrum engineering
disciplines:
- Data Structures & Algorithms (DSA)
- Live Bug Fixing & Defect Debugging
- Real-time Backend API Development (tested against live running microcontainers)
- Frontend UI Assembly (evaluated via Multi-Modal Vision LLMs)
- Prompt Engineering Duels (evaluated via semantic rubric grading & anti-bot checks)
- Full-stack Projects

The platform is designed to guarantee zero downtime, instant matchmaking (sub-15s
guarantee via 3-tier fallback), sub-millisecond leaderboard caching, low-latency
bi-directional telemetry via WebSockets, and zero-trust sandboxed execution for
user-submitted arbitrary code.

3.1. The Six Competitive Battle Disciplines
--------------------------------------------------------------------------------
1. DSA (Data Structures & Algorithms):
   - Real-time algorithmic head-to-head duels.
   - Concurrently executes compiled languages (C++, Java) and interpreted runtimes
     (Python, JavaScript, TypeScript) against secret test suites.
   - Measures CPU run time (down to milliseconds) and peak memory usage (MB).

2. Bug Fix:
   - Real-world codebase debugging under extreme time limits.
   - Injects syntactical, logical, off-by-one, race condition, or memory-leak bugs.
   - Players must read stack traces, isolate the failure, and patch the source.

3. Backend API Engineering:
   - Players are given a requirement spec (e.g., "Build an idempotent Stripe webhook
     or rate-limited auth endpoint").
   - Backend spins up an isolated Docker container, mounts the player's code, boots
     the web server, and runs automated HTTP integration test suites over localhost.

4. Frontend Layout Assembly:
   - UI development duels where developers build responsive components matching
     a design mockup and design requirements.
   - Evaluated by Multi-Modal AI Vision LLMs comparing visual rendering, flexbox/grid
     compliance, and component architecture.

5. Prompt War:
   - Advanced prompt engineering duels.
   - Contestants craft zero-shot, few-shot, or chain-of-thought prompts to solve
     complex generative logic or extraction tasks.
   - Evaluated by multi-criteria rubrics, with built-in heuristic AI-text detection
     to prevent users from copying raw AI output.

6. Full-stack Projects:
   - Comprehensive multi-tier challenges evaluated on backend persistence, API
     robustness, and UI interaction.

3.2. Three-Tier Matchmaking Engine (Live -> Ghost Replay -> AI Bot)
--------------------------------------------------------------------------------
To solve the "cold start" and player desertion problem common to multiplayer games:
- Tier 1: Real-Time Human Queue
  Scans active Socket.IO connection pools for online players within a +/- 150 Elo
  bracket. Widens bracket by 50 Elo every 3 seconds up to 15 seconds.
- Tier 2: Ghost Opponent Replay
  If no human is found within 15 seconds, the engine queries MongoDB for past human
  matches on the same problem with similar Elo. It streams the recorded submission
  timeline as an active "Ghost", simulating keystrokes, compilation attempts, and
  progress bar updates in real time.
- Tier 3: Adaptive AI Bot Simulator (`devbot_v1`)
  If no ghost recording matches the criteria, an AI bot agent simulates a player.
  It calculates target solve times based on user rating, simulates human-like typing
  jitters, occasional failed compile runs, and final submission.
Result: Queue wait times never exceed 15 seconds.

3.8. Elo Rating Mathematics & Anti-Cheat Moderation
--------------------------------------------------------------------------------
- Standard Elo formula adapted for competitive programming:
    E_A = 1 / (1 + 10^((R_B - R_A) / 400))

- Dynamic K-factor:
    K = 40 for provisional users (< 10 matches) to rapidly converge rating.
    K = 20 for established players.
    K = 10 for master-tier ratings (> 2000 Elo).
- Anti-Cheat: Code plagiarism heuristics, sandbox jail-break detection, and
  tab-focus loss telemetry during live ranked matches.

4.1. Challenge 1: The AI Gateway Model Deprecation & Dead Key Collapse
--------------------------------------------------------------------------------
THE PROBLEM:
During peak testing, Groq suddenly decommissioned several model endpoints
(such as `llama-3.3-70b-versatile`), returning HTTP 404 `model_not_found` errors.
Concurrently, several free-tier developer API keys hit their daily limits or were
revoked, returning HTTP 401 `Invalid API Key`.
Because AI evaluation is used directly in Frontend, Prompt War, and match code
reviews, these upstream API errors caused uncaught promise rejections, hanging
matches, and infinite waiting spinners for end users.

HOW WE TACKLED IT:
1. Multi-Model Fallback Chain (`aiGateway.service.ts`):
   Instead of hardcoding a single LLM model, we implemented an automated fallback
   cascade. If the primary model (`llama-3.3-70b-versatile`) throws a 404 or 400,
   the catch block immediately catches the error, remaps the target model to
   `llama-3.1-8b-instant` or official replacements (`gpt-oss-120b`, `qwen-3.6-27b`),
   and retries the inference request seamlessly without dropping the user's call.
2. Self-Healing Key Health Scanner & Auto-Pruning:
   In `aiGateway.service.ts` and `admin.controller.ts`, we added an automated
   verification scanner. When a key throws an HTTP 401:
   - The key is immediately flagged as `isActive: false` in MongoDB.
   - It is bypassed in memory for all subsequent key rotations.
   - We exposed an administrative endpoint `POST /api/v1/admin/api-keys/prune` that
     iterates through all configured keys, makes a lightweight 1-token probe call,
     and deletes or disables all defunct credentials automatically.
3. Decrypted Key Memory Caching:
   AES-256 decrypted keys are cached in memory with a 5-minute TTL, avoiding
   repeated database decryptions on every evaluation.

4.2. Challenge 2: High-Concurrency Battle Room Timer Leaks & Zombie Processes
--------------------------------------------------------------------------------
THE PROBLEM:
Every active battle room requires countdown timers, round timers, and latency
heartbeats. Initially, timers were spawned using standard `setInterval` inside
Socket.IO handlers.
When players disconnected abruptly, closed browser tabs, or encountered network
drops, the corresponding socket disconnected, but the underlying `setInterval`
continued ticking in Node.js memory. Over 100+ concurrent matches, thousands of
unreferenced timer intervals accumulated in the V8 event loop, causing CPU
utilization to spike to 100% and triggering out-of-memory (OOM) crashes.

HOW WE TACKLED IT:
1. Centralized Room Registry with Strong Lifetime Management:
   We created a centralized `ActiveBattleRooms` map holding explicit references to
   all active room timers, socket IDs, and abort controllers.
2. Safe Cleanup Lifecycle Hooks:
   In `battle.controller.ts` and Socket disconnect listeners:
   ```typescript
   if (room.timerInterval) {
     clearInterval(room.timerInterval);
     room.timerInterval = null;
   }
   if (room.abortController) {
     room.abortController.abort();
   }
   ```
3. Node-Cron Stale Room Sweeper (`staleBattleRoomCleanup.ts`):
   A background job runs every 10 minutes scanning MongoDB for rooms in `in_progress`
   status that have had no socket activity for > 30 minutes. It forcibly terminates
   them, clears lingering intervals, refunds disconnected players' Elo ratings
   if caused by server maintenance, and marks the room `abandoned`.
4. Unlimited Clock Format Support:
   Refactored the clock math to support variable time structures (unlimited practice,
   blitz 5-min, standard 15-min) without relying on ticking countdown intervals for
   static displays.

4.3. Challenge 3: 2,000-Connection Traffic Surge & Database Pool Starvation
--------------------------------------------------------------------------------
THE PROBLEM:
Stress testing the platform under a simulated 2,000 concurrent user barrage
revealed severe bottlenecks:
1. MongoDB default connection pool (`maxPoolSize: 10`) was exhausted in seconds.
   Database queries queued up, causing HTTP 504 Gateway Timeouts.
2. The `/api/v1/leaderboard/global` endpoint was recalculating ranks across tens
   of thousands of user documents on every single request, performing full table
   scans (`COLLSCAN`) that crippled the database.
3. Single-threaded Node.js event loop saturation delayed WebSocket packet delivery.

HOW WE TACKLED IT:
1. Multi-Replica Backend Scaling (`docker-compose.yml` & `nginx.conf`):
   Configured 4 Express backend container replicas (`backend-1` through `backend-4`)
   bound to ports 8000–8003. Host Nginx was configured with an `upstream` block
   using round-robin load balancing and persistent HTTP keepalive pools:
   ```nginx
   upstream backend_servers {
     server 127.0.0.1:8000 max_fails=3 fail_timeout=10s;
     server 127.0.0.1:8001 max_fails=3 fail_timeout=10s;
     server 127.0.0.1:8002 max_fails=3 fail_timeout=10s;
     server 127.0.0.1:8003 max_fails=3 fail_timeout=10s;
     keepalive 256;
   }
   ```
2. Mongoose Pool Expansion:
   In `backendServer/src/db/connectDB.ts`, we increased `maxPoolSize` from 10 to
   100 per container instance (400 concurrent database connections total):
   ```typescript
   await mongoose.connect(process.env.MONGODB_URI!, {
     maxPoolSize: 100,
     minPoolSize: 10,
     serverSelectionTimeoutMS: 5000,
   });
   ```
3. Compound Covered Indexing (`IXSCAN`):
   Added compound indexes on `userProfile.model.ts`:
   `{ "ratings.dsa": -1, userId: 1 }`
   This allows MongoDB to satisfy leaderboard sorting and pagination directly from
   RAM index trees without reading document bodies from disk.
4. Redis RAM Response Caching Middleware (`cache.middleware.ts`):
   Wrapped read-heavy routes in Redis caching with automatic invalidation on new
   match completions.
   BENCHMARK RESULT: Leaderboard throughput surged from 140 RPS to 17,088 RPS
   with 0 ms median latency!

4.4. Challenge 4: Next.js 16 / React 19 Hydration Failures & Inline Script Panics
--------------------------------------------------------------------------------
THE PROBLEM:
Upgrading to Next.js 16 (Turbopack) and React 19 introduced strict rules regarding
client hydration and script execution:
1. Client-side console error:
   "Encountered a script tag while rendering React component. Scripts inside React
   components are never executed when rendering on the client."
   This occurred because theme-switching scripts and third-party badges (DMCA)
   were injected as raw `<script>` tags inside `layout.tsx`.
2. Hydration mismatches: LocalStorage theme values ('dark' vs 'light') differed
   between the server-rendered HTML and client DOM, causing layout flashing
   and broken React reconciliation trees.

HOW WE TACKLED IT:
1. Standardized JSON-LD Structured Data:
   Replaced manual script injections with explicit Next.js React 19 compliant data
   scripts:
   ```tsx
   <script
     type="application/ld+json"
     dangerouslySetInnerHTML={{ __html: JSON.stringify(schemaGraph) }}
   />
   ```
2. Headless Script Offloading:
   External scripts (e.g., `DMCABadgeHelper.min.js`) were refactored using Next.js
   `<Script strategy="lazyOnload" />` placed cleanly inside the `<body>` element.
3. Flawless Theme Hydration Pattern:
   Removed inline script hacks in favor of Zustand-backed persistent theme store
   coupled with CSS variables and `suppressHydrationWarning` on the `<html>` root:
   ```tsx
   <html lang="en" suppressHydrationWarning className={theme}>
   ```
   An `initTheme()` hook executes in `providers.tsx` on client mount, reading
   `localStorage` and applying the appropriate class without breaking server SSR.

4.5. Challenge 5: Backend API Battle Sandbox: Ephemeral Docker Container Orchestration & Port Collisions
--------------------------------------------------------------------------------
THE PROBLEM:
In the Backend Battle discipline, users submit complete Express/Nest/Fastify
server code. We must run their code in an actual execution environment, listen
on a port, and fire automated test suites against it.
Critical risks:
1. Malicious user code attempting to access host filesystem or network.
2. Port conflicts when multiple concurrent matches run on port 3000/8000.
3. Zombie containers failing to exit when user code contains infinite loops
   (`while(true)`) or unhandled errors.

HOW WE TACKLED IT:
1. Dynamic Ephemeral Container Lifecycle (`backendJudge.service.ts`):
   When a submission is received:
   - A unique directory `/tmp/submissions/{submissionId}` is materialized.
   - A free ephemeral port (e.g. `49152–65535`) is allocated dynamically.
   - A Docker container is booted with strict security flags:
     `docker run -d --rm --memory="256m" --cpus="0.5" --pids-limit=64 --network none -p {randomPort}:8000 ...`
2. Aggressive Health Checks with Timeout Cutoffs:
   A lightweight polling loop probes `http://localhost:{randomPort}/health`
   every 100ms for up to 3000ms. If the user's server fails to boot within 3 seconds,
   the container is killed via `docker rm -f`, and a `Server Boot Timeout` error
   is returned.
3. Automated Test Suite Execution:
   Once the container is healthy, our backend issues an array of HTTP requests
   (GET, POST, invalid bodies, edge cases) against the container, measures response
   codes, headers, and payloads, and grades the submission.
4. Guaranteed Destruction via `finally`:
   Container removal is wrapped in a `try...finally` block to ensure that win, lose,
   crash, or timeout, the container is destroyed and temporary files are unlinked.

4.6. Challenge 6: Matchmaking Desertion & Low-Traffic Ghost Opponent Replay
--------------------------------------------------------------------------------
THE PROBLEM:
In real-time multiplayer platforms, user retention drops dramatically if players
are forced to wait longer than 30–60 seconds for a human opponent. In early
stages or during off-peak time zones, matching human players of equal skill is
statistically impossible without a massive concurrent player base.

HOW WE TACKLED IT:
1. Ghost Opponent Data Harvesting:
   Whenever a human user completes a battle, their submission data, keystroke
   milestones, compilation attempts, and execution timings are stored in MongoDB
   under `Match.model.ts` as an eligible Ghost Replay.
2. Seamless Ghost Streaming (`matchmakingFallback.service.ts`):
   When a player waits > 15 seconds in queue, the engine transitions the room to
   Ghost Mode without informing the client UI (preserving psychological tension).
   The engine reads the ghost player's submission profile, masks their presence
   as a live player, and schedules progress bar emissions at the exact timestamps
   recorded in the original match.
3. Dynamic Fallback to Bot Simulator (`botSimulator.service.ts`):
   If no ghost match exists for that specific problem, `devbot_v1` is spawned.
   The bot's target completion time is calculated as a function of the problem
   difficulty and the human player's Elo, guaranteeing a fair and competitive match.

4.7. Challenge 7: Automated Frontend Visual Evaluation Without Unit Tests
--------------------------------------------------------------------------------
THE PROBLEM:
Grading frontend code (HTML/Tailwind/CSS/React) through unit tests (Jest/Testing
Library) is brittle. Minor class differences (e.g., `flex items-center` vs
`grid place-content-center`) can achieve the exact same visual layout while failing
strict string or DOM equality tests.

HOW WE TACKLED IT:
1. Multi-Modal Vision & Structural Rubric Evaluation (`frontendJudge.service.ts`):
   We designed an AI Vision pipeline.
   - Step 1: Structural Extraction. The user's submitted DOM/JSX and CSS rules
     are parsed for semantic structure, layout hierarchy, and responsiveness.
   - Step 2: Reference Comparison. The submission is evaluated alongside the
     reference challenge rubric.
   - Step 3: LLM Evaluation. The code is passed to Grok Vision / Llama Scout with
     a structured prompt requiring a strict JSON output schema containing:
     `{ visualAccuracy: 0-100, responsiveScore: 0-100, codeQuality: 0-100, feedback: string }`.
2. Deterministic Scoring Normalization:
   The composite score is calculated using weighted multipliers:
   `FinalScore = (visualAccuracy * 0.5) + (responsiveScore * 0.3) + (codeQuality * 0.2)`.
   This allows flexible engineering approaches while strictly enforcing visual
   fidelity and design specifications.

--------------------------------------------------------------------------------
4.8. Challenge 8: Microcaching Dynamic SSR Routes Without Corrupting Real-Time Sessions
--------------------------------------------------------------------------------
THE PROBLEM:
Next.js SSR provides incredible SEO and initial page load speed. However, rendering
React components on the server for every incoming request under high traffic spikes
strains the Node.js event loop.
If we cache the entire application indiscriminately in Nginx, user-specific
authenticated states (profile avatars, notifications, active battle redirects)
leak across different users' browsers.

HOW WE TACKLED IT:
1. Strict Route Segregation:
   We divided the URL topology into two distinct categories:
   - Category A: Static & Public Documentation (`/`, `/about`, `/faq`, `/guidelines`,
     `/privacy`, `/terms`, `/contact`).
   - Category B: Dynamic & Authenticated App Routes (`/battle/*`, `/dashboard`,
     `/profile`, `/api/*`).
2. Nginx Microcaching with Header Overrides (`nginx.conf`):
   For public pages, Nginx enforces a 2-second RAM microcache:
   ```nginx
   proxy_cache STATIC_CACHE;
   proxy_cache_valid 200 2s;
   proxy_ignore_headers Cache-Control Expires Set-Cookie;
   proxy_cache_use_stale error timeout updating http_500 http_502 http_503;
   ```
   A 2-second microcache is imperceptible to users looking at landing page copy,
   yet absorbs thousands of duplicate requests per second during viral spikes.
3. Edge Caching Headers (`next.config.ts`):
   Public routes emit explicit edge caching headers:
   `Cache-Control: public, max-age=3600, s-maxage=86400, stale-while-revalidate=604800`
   Dynamic app routes emit:
   `Cache-Control: private, no-cache, no-store, must-revalidate`

4.9. Challenge 9: WebRTC Voice Signaling NAT Traversal in Fast-Paced Matches
--------------------------------------------------------------------------------
THE PROBLEM:
Integrating live in-match voice chat required direct peer-to-peer audio streaming
between players. Due to asymmetric NATs, cellular data connections, and firewalls,
direct WebRTC connections frequently failed or entered disconnected states,
leaving players with silent or broken audio channels.

HOW WE TACKLED IT:
1. Robust Signaling State Machine (`battleVoice.socket.ts`):
   Built a signaling coordinator over Socket.IO handling:
   - `voice-join-room` -> Notifies opponent and initiates handshake.
   - `voice-offer` -> Relays SDP offer with ICE restart flags.
   - `voice-answer` -> Relays SDP answer.
   - `voice-ice-candidate` -> Buffers and exchanges ICE candidates.
2. Redundant STUN Server Configuration:
   Configured multiple public Google STUN servers (`stun:stun1.l.google.com:19302`,
   `stun:stun2.l.google.com:19302`) in client WebRTC peer connection options.
3. Graceful Fallback & Mute Telemetry:
   If WebRTC peer connection status transitions to `failed` or `disconnected`,
   the client UI updates the voice pill to `Disconnected` without throwing
   unhandled exceptions or interrupting the ongoing code battle.

4.10. Challenge 10: Asynchronous OTP/Email Delivery Failures Under Load Spikes
--------------------------------------------------------------------------------
THE PROBLEM:
When many users sign up simultaneously, sending transactional verification OTP
emails synchronously during HTTP request handling causes requests to hang for
1–3 seconds while waiting for SMTP handshakes. If the SMTP server experiences
rate limiting or network latency, the signup API endpoint times out.

HOW WE TACKLED IT:
1. BullMQ + Redis Decoupled Producer-Consumer Architecture:
   Separated email dispatch into a non-blocking queue (`emailQueue.ts`).
   The registration controller pushes a job to Redis in < 2 milliseconds and
   immediately returns HTTP 201 to the client.
2. Dedicated Worker Container (`emailWorker.ts`):
   A standalone worker process pulls jobs from Redis with concurrency throttled
   to 5 parallel transmissions, preventing SMTP server rejection.
3. Exponential Backoff & Dead Letter Handling:
   Configured 3 automated retry attempts with exponential backoff:
   `attempts: 3, backoff: { type: 'exponential', delay: 2000 }`.
   Failed jobs are moved to a Dead Letter Queue for administrative review.
